我还是想走捷径，所以想练练第一性原理

发表于2026-11-25|更新于2026-11-25|心理
|阅读量:|评论数:

假设有个订单列表，打开很慢。有人说，查订单总数的那条 SQL 太慢了，给它加个索引吧。

我挺喜欢这种提议。问题具体，改动有着落，改完还能量一下快了多少。可我想给自己练一个新习惯：在打开数据库之前，先打开那个订单页面，看一眼「共多少条」到底写在什么地方。

万一页面上根本没有这个数字呢？

那条 SQL 到底是谁要的

把例子补全一点。假设页面每次显示二十条订单，下面只有一个「加载更多」按钮，既不显示总数，也不能跳到最后一页。后端用了一个通用分页组件，取订单列表的同时，顺便查出满足条件的订单一共有多少条。前端虽然不展示总数，却用它判断按钮还能不能点。所以这条查询不能直接删，删了按钮就坏了。

那按钮非得知道总数吗？它其实只需要知道：这二十条后面，还有没有至少一条？

这样就有了另一个方案：按同样的筛选条件和稳定的顺序，多取一条。拿到第二十一条，就只展示前二十条，保留按钮；只拿到二十条或更少，就不再显示按钮。总数可以不知道。然后用恰好二十条、二十一条的数据各试一次，再对比改动前后的请求耗时。快没快、按钮对不对，是两件事，都得看。

我说的第一性原理，就在中间那个小转弯里。目标是让人尽快看到订单，同时不能把后面的订单藏起来；「接口要返回准确总数」是现有实现替我选的办法。把这个办法暂时拿掉，再从页面必须做到的事往回推，才发现这个场景只需要一个“是”或“否”。

当然，换个页面，答案马上就变。如果这是财务对账页，用户得拿筛选后的准确笔数去核账，二十一条就回答不了他的问题。这时该优化查询就优化查询。第一性原理没有规定我一定得删掉什么，它只是让我知道，什么能删，什么删了就不再是同一件事。

电梯里那面镜子，帮不了赶时间的人

我也容易把“换个角度问问题”都叫作第一性原理。拿电梯举例：有人抱怨等太久，给等候区放面镜子，让人等的时候有事可做。这是个挺巧的主意，我喜欢它的巧，可它到底解决了谁的问题？

如果楼下没几个人，乘客只是不知道电梯来没来、还要等多久，楼层提示可能比镜子更有用。如果早上九点，电梯连着三趟满员，一个人眼看就要迟到，他照完镜子还是挤不上去。他缺的是高峰时段能把人送上楼的运力。去现场看看有多少人没能上第一趟，比继续猜他们等得有多无聊靠谱。

这里有两步很容易混在一起。“也许他说的慢，是觉得难熬”，是在提出另一种解释；“就算站在这儿不无聊了，满载的轿厢还能不能多装一个人”，才是在检查哪条约束绕不过去。前一步让我多一个主意，后一步有时会让我舍得放弃这个挺聪明的主意。

我不想把自己练成一个凡事都要从头推的人

我本来就偏结果导向。东西坏了，我想先让它能用；有条走得通的近路，我也不想为了显得思考深刻，非绕一圈。比如线上刚出了故障，有已经验证过的回滚办法，那就先恢复服务。等人不用守着报警了，再讨论为什么每次发布都可能遇到同一个坑。

我真正想练的，是在不着急、而且做错会白忙一阵子的时候，把求解往后放一两分钟。拿张纸写两行就好：

对方必须能做到什么？

我正准备做的事，哪一部分只是因为「以前一直这么做」？

如果还是拿不准，我会给自己的答案找个反例。就像刚才那个财务：只要他真的需要核对笔数，我自以为漂亮的方案就得重想。这时找个人或者找 AI 来挑毛病，都比让它直接给我列「十种优化 SQL 的办法」更有用。前提是，我先把自己的判断写出来，不然被挑毛病的还是别人的答案。

我还没把这练成习惯，也不指望每道题都能拆出一条捷径。下次碰到慢查询，最后可能还是老老实实加了索引。只要动手之前，我能指着页面说清楚“就是这个人，在这里，真的需要这个数”，那一两分钟就没有白花。
